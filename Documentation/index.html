01

Index.ts

This is the main file. It sets everything up and then runs the scenes.

The canvas is the box on the page where the 3D scene is made. The engine is Babylon.js's renderer. There is one canvas and one engine, and all four scenes share them.

The scene list

scenes holds the four scenes once they're built. Index 0 is Scene 1, index 1 is Scene 2, and so on. activeSceneIndex says which one is on screen at that time.

Main()

Main() waits for Havok to load first, because the physics can't start without it. Then the loop builds each scene, adds physics, then adds the farmer player controller. The farmer takes a moment to load, which is why there's an await present. The render loop runs each frame. It checks for the player crossing the edge, then renders only the active scene. The other scenes are "frozen" until the player goes back to them.

Arrow keys and the camera

By default, the arrow keys spin the camera. The player uses the arrow keys too, so this line turns that off for the camera. You can still drag with the mouse to look around.

02

Physics: the floor and walls

The player is moved by a physics engine, so each scene needs physics switched on and something solid to stand upon. That's what the addPhysics function does.

enablePhysics takes the gravity and the physics plugin. Gravity is -18 on the Y axis, which is stronger than real life so jumps feel snappy. The havok object is the one loaded earlier.

The solid helper makes a box, places it, hides it and gives it a physics body. Mass: 0 means the box is fixed in place. Nothing can push it around.

The floor is a flat sheet with no thickness, and physics needs something with depth to stand on. So there's an invisible box, 1 unit thick, sitting just under it. Its top is at height 0, level with the ground which the player can see.

Four invisible walls sit just outside the ground (at 7.5, where the ground ends at 7). They're 4 units tall, so the player can't walk or jump over them. Hidden meshes still collide, which is why isVisible = false is enough.

03

Scene transitions

Two scripts work together for this part. sceneTransitions.ts answers the question "has the player reached the edge of the scene, which edge, and what scene do I pick?" index.ts works with that answer.

The code gives it the current scene index and the player's current position. It returns either null or a destination scene and the spot to move the player to when it loads.

Edge = 6
How far from the centre of the scene the player has walked to trigger an exit. The ground ends at 7, so this is just before the edge.
Spawn = 5
Where the player appears in the next scene. It's a bit inside the edge on purpose. If the player was placed at 6 it would trigger going back to the previous scene.
Y = 0.9
The height of the middle of the player's model, so the player appears standing on the ground.

The player comes in on the opposite side from where they left. Walk out of the right edge and they appear at the left of the next scene.

The check in index.ts

This runs once per frame, before rendering. It looks at where the player is. If they passed an edge, it makes the next scene the active one and moves that scene's player to the spawn point. Each scene has its own player, so the one in the next scene is moved, not the one the player left behind.

teleportFarmer is used rather than setting the position directly. The physics controller keeps its own idea of where the player is and would overwrite a direct change on the next frame. teleportFarmer updates both.

04

The four scene files

Each of the scene1 to scene4 folders contains a createStartScene.ts. They are almost identical! Only the ground colour and the assets change.

Light
a soft light from above that lights the whole scene evenly.
Ground
a flat 14 by 14 squares. It forms from -7 to 7 in both directions, which is where we get the edge numbers from.
Camera
an orbit camera that circles the point (0, 1, 0). It starts 14 units away, looking towards the far edge. It doesn't follow the player's model. The whole scene fits in the view.

Each model file is loaded once. The first copy goes at the first position, then it's simply cloned for every other position. That's why a call like this puts two trees in the scene while only loading the file once.

loadEnvironment just creates an AssetsManager, runs the list of addAsset calls, and starts loading. It also prints an error in the console if a file is missing.

The scenes

Scene 1
Contains a woodland clearing inspired scene, with nice bushes, ferns and flowers and a fresh green aesthetic.
Scene 2
Showcases an overgrown scene with dead and twisted trees, rocks and mushrooms.
Scene 3
Shows a pine grove with pebbles, clover and a small stone path.
Scene 4
Holds a bright, colourful garden with flowers and a stepping-stone path.

The trees and rocks are only for looks and don't contain any physics, so the player doesn't get stuck (they can walk right through them).

05

The player

createCharacterController.ts runs once per scene. It creates the player, listens to the keyboard inputs and moves the player every frame.

These are the values you'd change to alter the sensitivity and speed. Walking speed is moveSpeed, and airSpeed is the slower sideways speed while jumping.

The physics body

Physics treats the player as an invisible capsule 1.8 units tall. The capsule is what bumps into walls and stands on the floor. The player model is just a picture that follows it around. The position starts at half the capsule's height, so he begins standing on the ground.

The player model

The model file comes with lots of separate meshes. They are all attached to one empty node named farmerRoot, so moving that one node moves the whole farmer player model. It's saved as sceneData.farmer, which is what index.ts reads when it checks for edges.

The animations come in with the model. The code looks for one called Idle_Neutral (or Idle) for standing and Walk (or Run) for moving, and starts with the idle animation playing.

Reading the input

keys contains a list of the keys held down at that time. A key goes in when you press it and comes out when you let go. Pressing space doesn't jump immediately. It sets jumpRequested, and the frame update picks it up.

The frame update

This is the main part. It runs before every frame is made.

The controller asks whether there's something under the capsule. If so, the player is on the ground. If not, the player is in the air.

D and right-arrow keys push x up, A and left-arrow push it down. The same goes for W, S, up and down arrows on z. If the player holds two keys at once, the code scales the direction down so going diagonally isn't faster than going straight.

Jumping
the upward speed is set from the jump height and gravity, using Math.sqrt(2 * gravity * jumpHeight), which is the speed needed to reach that height exactly.
In the air
sideways movement is allowed at the slower airSpeed and gravity pulls the player down every frame.
On the ground
the controller works out the walking velocity following the surface under the player.

Integrate is the step where the controller moves the player, stopping it at the walls and floor.

The capsule's position is its origin, its middle. But the feet of the model should be at the bottom. So half the capsule's height is taken off.

If the player is moving, play the walk animation. If not, play idle. While the player moves, turn to face the direction the player is moving. Atan2 converts a direction into an angle.

Teleporting

This is what index.ts calls when the player crosses an edge. It moves the physics capsule and the farmer model at the same time. setVelocity stops the player from carrying their old speed into the next scene.

06

Havok.ts and interfaces.d.ts

Havok is the physics engine. It's written in WebAssembly, so the browser must download a .wasm file before it can use it. This function tells Havok where to find that file (Babylon.js's own server) and waits until it's ready. Index.ts calls it once and hands the result to every scene. This file does not change.

This code shows what each scene keeps: the scene itself, the lighting, ground, camera and the player's values. The "?" means "might not be there yet". For example, farmer doesn't exist until the model has finished loading. It's only for TypeScript's error checking and does nothing when the code runs.
